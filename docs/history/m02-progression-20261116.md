## 增量检查发现的 DPX 地址缓存缺陷

当前本机 SDCC-4.6.0-MCS251 在以下语句序列中生成错误地址：

```c
S7CON &= 0xFEU;
last_rx = 0x41U;
++rx_count;
S7CON &= 0xFDU;
```

`S7CON` 为 `(*(volatile __xdata unsigned char *)0x7EF7A0UL)`，两个变量均为 XDATA 全局对象。独立复现源码与汇编位于：

- `.cache/m02-progression-20261116/dptr-repro.c`
- `.cache/m02-progression-20261116/dptr-repro.asm`

计数末尾生成 `mov dptr,#_rx_count` 与 `mov dpxl,#(_rx_count >> 16)`，使 DPX 指向计数对象。之后第二次 S7CON 访问却直接执行：

```asm
mov dr28,dpx
mov a,@dpx
mov r7,a
anl ar7,#0xfd
mov dr28,dpx
mov a,r7
mov @dpx,a
```

这里没有重装 `0x7EF7A0`，也没有把 DR28 复制回 DPX，因此实际访问仍落在计数对象。这不是 C 代码中的地址设置行为，也不能用 volatile 保证来解释为合法优化。只通过编译和汇编核查即可复现，无需连接硬件。

本次在兼容例程中调整操作顺序：先完成 S7CON 清标志和 S7BUF 发送，再记录 last_rx/rx_count；随后的发送等待循环入口明确重新装载 S7CON 地址。已检查修改后的汇编，循环入口包含 `mov dptr,#0xf7a0`、`mov dpxl,#0x7e`。发送完成后才增加 tx_count。

这是当前示例的局部规避，不是对编译器的全局修复；后续增加交错 XFR/XDATA 操作时仍需检查生成代码。未修正版保存在 `02-counters/` 作为证据，不用于推荐下载；修正版另存 `02-counters-fixed/`。

修正版 HEX SHA-256：`AACB62878AD8F587881259921E955AB5635DDBB7B199C2A3E0EBE064379E8EB2`；默认 `build/Debug/firmware/STC32G144K246_Simulation_Test.hex` 已更新为这个修正版。
