# STC32G144K246 USB ISP 抓包命令证据

本页使用模板工程中 7 份 USBPcap 抓包重新解析得到。解析脚本会先按 USB 端点重组完整 ISP 帧，再检查方向字节、长度、校验和和结束字节 `0x16`。7 份抓包共得到 2145 个完整 ISP 帧，解析错误为 0。

解析脚本和逐帧结果位于本目录的 `commands-*` 文件夹中。

## 命令结构

| 方向 | 命令 | 数据长度 | 应答 | 证据 |
| --- | ---: | ---: | --- | --- |
| 主机发出 | `00` | 1 | `00` 状态帧，54 字节 | 所有下载会话 |
| 主机发出 | `01` | 8 | `01` | 所有完整配置下载 |
| 主机发出 | `03` | 5 | `03`，8 字节，包含型号识别码 | 所有完整配置下载 |
| 主机发出 | `05` | 5 | `05` | 所有完整配置下载 |
| 主机发出 | `02` | 133 | `02 54` | 程序块，128 字节数据 |
| 主机发出 | `04` | 46 | `04 54` | 硬件配置 |
| 主机发出 | `32` | 133 | 抓包中随后继续状态查询 | EEPROM 第一个块 |
| 主机发出 | `12` | 133 | 抓包中随后继续状态查询 | EEPROM 后续块 |
| 主机发出 | `FF` | 1 | 无单独应答 | 退出 ISP |

## 地址字段

在 F8D1 的 128 字节数据块中，完整载荷的前五个字节为命令、低地址字节、地址中间字节、块类型和地址高字节。地址计算为：

```text
address = 0xFC2800 + (payload[4] << 16) + (payload[1] << 8) + payload[2]
```

抓包结果确认：

| 命令 | 地址范围 | 说明 |
| ---: | --- | --- |
| `02` | `0xFF0000` 开始，每块 `0x80` 字节 | 程序区连续写入 |
| `32` | `0xFC2800` | EEPROM 第一个块 |
| `12` | `0xFC2880` | EEPROM 连续块 |

## 配置帧

配置帧固定为 46 字节，前五字节是：

```text
04 00 00 5A A5
```

后 0x28 字节由主机的硬件选项组包函数生成。7 份抓包中配置帧数量如下。

| 抓包 | 配置帧 | 程序块 | EEPROM 块 |
| --- | ---: | ---: | ---: |
| 基线 | 1 | 16 | 0 |
| 24 项硬件选项 | 23 | 384 | 0 |
| IRC 与用户系统区 | 5 | 80 | 0 |
| P3.2/P3.3 | 2 | 32 | 0 |
| EEPROM 单块 | 1 | 16 | 1 |
| EEPROM 双块 | 1 | 16 | 2 |
| IRC 频点复测 | 14 | 224 | 28 |

## 配置和应答的静态对应

- `04 54` 是硬件配置写入成功应答。
- `02 54` 是程序块成功应答。
- `00` 应答包含芯片当前状态、型号识别码、容量和硬件选项回读数据。
- `03` 应答中可直接看到 `F8D1`，说明该阶段负责确认芯片型号和下载协议族。
- EEPROM 单块和双块抓包显示，EEPROM 可以和程序区一起放入同一个 HEX 下载流程，主机按地址选择 `32` 和 `12`，不需要独立的“只下载 EEPROM”界面协议。

## 与静态逆向的对应

| 抓包现象 | 6.97C 主机代码 |
| --- | ---: |
| 配置写入 | `0x44D036`、`0x44D068` 调用 `0x44B760` |
| 程序块发送 | `0x44CDAB` 附近构造 128 字节块并调用 `0x44BB90` |
| EEPROM 块发送 | `0x44CF40` 等路径发送 `0x32`、`0x12` |
| 发送与接收 | `0x44BB90`、`0x44BAB0` 的 USB HID 收发包装 |
| 退出 ISP | 任务结束阶段写出 `0xFF` |

这些抓包验证了 STC32G144K246 F8D1 的命令结构。它们不能直接证明所有 1345 个型号共用相同的地址基址和配置载荷长度。型号差异仍由 [型号数据库](models-6.97c.json) 的型号识别码、配置族和 `config_layout` 提供。
