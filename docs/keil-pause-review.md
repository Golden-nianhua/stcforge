# Keil 原生 USB-ICE 暂停路径复核

日期：2026-11-15。范围限定为本机 STCMON251.DLL 静态读取和已有 keil sma 原始抓包；未加载或执行 DLL、未枚举或打开硬件，未改动 src/tests。本报告不把启动顺序对齐或运行确认成功表述为运行失联已修复。

## 结论

本机 DLL 没有导出 AG_Stop。实际停止入口是导出 AG_GoStep（RVA 0x15C1）的操作值 1 分支，调用内部停止包装函数 0x48AD，再由 0x1F22 的原生 USB 分支发送 FF5A030002A2。这个发送分支本身不等待 ACK，不读取寄存器，也不发送 run。

正在执行的 AG_GoStep(4) 路径在另一段控制流中等待停止事件；收到后读取空间 0、地址 0、数量 4 的 PC，按需要恢复软件断点，再读取完整 46 字节 CPU 状态。抓包中两次显式暂停都与此吻合。

最重要的静态发现：虽然等待接口传入 1000 ms，原生 USB mode 0 的收包分支没有检查该超时参数。ReadFile/GetOverlappedResult 失败也没有在读帮助函数中区分“尚未完成”和其他 I/O 错误。因此在这段 DLL 控制流内，不能认为官方会在 1 秒无响应后自动重试、补发 halt、查询备用快照或恢复设备；未见这些分支。外层 Keil 是否另有取消、看门狗或进程处置机制，本次没有证据。

## 确切入口和调用链

| RVA | 静态作用与关键证据 |
| --- | --- |
| 0x15C1 | AG_GoStep 导出入口；0x15D9..0x15EA 按第一个参数 1/2/3/4 分派。 |
| 0x1697 | 操作 1 分支：call 0x48AD；把返回值留在 EBX，并在 0x16A1..0x16A3 将全局 0x10818 设为 1。 |
| 0x48AD | 检查全局 0x10814。非零时 call 0x1F22、返回 0；为零时直接返回 1。结合运行入口赋值，将它解释为执行中标志。 |
| 0x1F22 | 停止发送帮助函数；0x1F37..0x1F55 的 mode 0 分支构造 00 02、call 0x1F9D，随后返回。 |
| 0x1F9D / 0x22F1 | 按模式编码和发送；mode 0 使用 FF 5A、LEN、负加和校验，最终 call 0x1C2E。 |
| 0x15F0 / 0x15FC | AG_GoStep(4) 设 0x10814=1，调用 0x48C2(-1)。 |
| 0x48C2 | 运行控制主体；0x49EC 调用 0x2EA7 发送 run 并等第一条事件，0x49FA..0x4A27 等待后续停止。 |
| 0x2EA7 | 发 08 00，即 FF5A0308009C；call 0x239B(NULL, 0, 1000) 等第一条事件。 |
| 0x1CCA | 运行停止等待帮助函数；mode 0 参数 0 时调用 0x239B(NULL, 0, 1000)，参数非零时直接置返回值 1，不发报文、不读第二个报告。 |
| 0x413A | PC 读取：调用 0x2D92(buffer, 0, 4, 0)，即空间 0、地址 0、数量 4；解码后更新 0x10798 及宿主提供的 PC 指针。 |
| 0x462E | 断点安装/恢复帮助函数；mode 0 分支 0x469C..0x46E3 遍历已启用断点，参数 0 时写回各断点保存的原始字节。 |
| 0x451F | 清除状态/内存缓存标记，调用 0x441B 处理缓存；它不是线上 read_state 请求。 |
| 0x41AE | 若状态缓存无效且 0x10814 为零，调用 0x2B81 读取快照，转换、缓存寄存器并更新 PC。 |
| 0x2B81 | 发 00 01，即 FF5A030001A3；请求 0x2E=46 字节，传入等待参数 1000 ms。 |

原生 USB 的 mode 0 设置见 0x1ACC：83254CE0001000，即将全局 RVA 0xE04C 清零。不要把 mode 1/2/3 的分支混为原生 USB 行为。

运行中调用 AG_GoStep(1) 的可确认顺序：

1. 0x48AD 看见执行中标志后只发停止请求，返回 0。
2. 导出分支将 0x10818 设为 1。该标志在运行循环中作为退出请求检查；此时 0x10814 仍非零，0x41AE 不会提前发完整快照读取。
3. 已在等待中的运行路径收到一条停止事件，随后到 0x4AAB 调用 0x413A 读取 PC，并检查断点条件；因停止请求标志已置位，走 0x4AC8 的 0x462E(0) 恢复断点。
4. 返回 AG_GoStep(4) 的 0x1602 后，清除 0x10818，调用 0x451F 使缓存失效，再于 0x160D 清除 0x10814；尾部 0x16C5 调用 0x41AE，才读取完整快照。

若 0x48AD 发现本来未处于执行中，则直接返回 1，不发送新的暂停请求；导出分支清除执行中标志、使缓存失效，尾部可能读取快照。这里的 0/1 是该 DLL 的实际返回路径，不据此推断完整 AGDI API 返回码语义。

静态分析没有确认 Keil 通过哪一种线程或重入机制调用停止入口；上述只说明两条控制流及共享标志，不能当作宿主线程模型的证据。

## 暂停前后的寄存器和事件处理边界

- 原生 USB 手动暂停前，0x1F22 没有先读寄存器或改变 IE。首次暂停抓包也没有这类报文。
- 停止后官方先读 PC，再恢复已安装的软件断点，再获取快照。PC 的宿主寄存器缓存更新不等于向目标写 PC。
- 0x5945 和 0x5A77 确实在自由运行前后被调用，但入口分别在 0x5949、0x5A7C 检查 mode==2，原生 USB mode 0 直接跳过其内部处理。
- 抓包稍后的单步路径确有空间 4、地址 A8 的读改写，例如 1815/1818/1826/1830；它发生在单步请求 1823 周围，不能移作前两次手动暂停的必需步骤。
- 0x239B 在 mode 0、期望事件时检查报告字节 [0]=07、[1]=06、[7]=04、[2]=00，见 0x264E..0x2685；没有要求剩余四个内容字节全零。因此带 PC 的 06 事件可以通过这一检查。等待停止的调用传 NULL，不从事件内容提取 PC，而是另发 PC 读取。
- 在所核对的暂停链中，没有找到本项目那样的“将旧事件先排入队列”的机制。0x239B 调用 0x1BA7(NULL) 并不清空旧报告：0x1BAE..0x1BB5 对 NULL 立即返回 0，不发起读取。已有完成但未消费的报告究竟如何与宿主其他操作竞争，本次没有动态证据。

## 官方无响应和错误行为：静态证据

### 传入 1000 ms 不等于原生 USB 有 1 秒截止

0x1CCA 的 mode 0、参数 0 分支传入 0x3E8=1000，调用 0x239B(NULL, 0, 1000)。0x2EA7 的 run 确认等待、0x2B81 的快照读取也传入 1000。

但 0x239B 内有以下模式分支，地址已从原 DLL 独立解码：

```text
24D1  mov esi,[0x1000C040]       ; GetTickCount
24D7  call esi
24DC  call 0x10001BA7           ; 此次参数为 NULL，立即返回
24E1  cmp [0x1000E04C],edi      ; edi=0，即检查 mode 0
24E8  jne 0x10002511            ; 非 mode 0 才走截止检查
24F1  call 0x10001BA7           ; mode 0 首次读
24F9  jne 0x10002537            ; 有报告则解析
2502  call 0x10001BA7           ; mode 0 重复轮询
250A  mov [ebp-4],eax
250D  je 0x100024FB             ; 无报告就继续，无 Sleep/时长/停止标志检查
...
2525  call esi                 ; 非 mode 0 的循环才再次 GetTickCount
2527  sub eax,ebx
2529  cmp eax,[ebp+0x10]        ; 与传入 timeout 比较
252C  jb 0x10002511
```

所以静态可确认的是：若原生读始终不给出一个完成报告，mode 0 会持续轮询，不会由这个 1000 ms 参数退出。不能用此代码声称“官方暂停超时后自动补读快照”。

### 读取错误不会在这层变成明确断连返回

0x1BA7 使用 65 字节 overlapped ReadFile，完成后剥离报告 ID，复制 64 字节。

- 0x1BEC 调用 ReadFile 后，0x1BF2 直接返回 0；没有检查 ReadFile 的 BOOL 或 GetLastError。
- 0x1C07 调用 GetOverlappedResult(bWait=FALSE)。0x1C0F 遇到 FALSE 跳回 0x1BF2 返回 0，且保留全局 0x10884 的 pending 状态。
- 只有 GetOverlappedResult 成功时才复制报告、返回 1 并清除 pending。

因此这段代码没有把 ERROR_IO_INCOMPLETE 与其他读取错误区分开。若底层持续返回失败，静态控制流仍可能留在上述轮询，不能推断它会报告某个特定 Windows 错误码。本次没有执行 DLL 来观察该情形。

发送侧 0x1C2E 在 ERROR_IO_PENDING 时调用 GetOverlappedResult(bWait=TRUE)，也没有在这一调用中设置超时；0x1CBD..0x1CC6 无条件清除写入标志、返回 1。不要把它解读为完整的官方 I/O 故障处理策略。

### 确实存在的报错分支

如果收到了报告但事件/数据格式校验不通过，0x239B 可走 0x270B：MessageBoxA 显示以下原文，再将全局连接有效标志 0xE044 清零，调用 PostMessageA(hWnd=[0x10804], Msg=[0x10828], wParam=5, lParam=0) 通知宿主，然后返回失败。消息号来自运行时全局变量，本次未确定其具体数值或宿主处理语义。0x1CCA 也有类似失败处理分支。

```text
标题（RVA 0xF66C）：Connection Error
正文（RVA 0xF618）：Connection to target system lost !
                       Please reset your target system and try again .
```

这说明有“连接丢失”提示和通知宿主的路径；它不是原生 USB 无报告满 1 秒后的必达路径。没有证据表明此处自动复位、重新枚举、重开句柄、重新发送 pause/run 或下载程序。

## 仍未知的事项与适用范围

1. 抓包中的两次显式暂停都成功，没有暂停超时的官方抓包；无响应结论来自静态控制流，不是硬件复现。
2. 尚未核对外层 uVision 进程的线程调度、取消或看门狗，也未确认宿主如何处理上述消息，不能保证整个 IDE 永不超时或永远卡住。
3. 两条全零 06 的含义依赖发送顺序。抓包支持“run 后确认、随后停止”的归属，但事件本身没有标签，不能从内容证明固件内部区分机制。
4. 本报告不解释当前 SDCC 程序运行后暂停/备用快照超时的根因，也不建议据此照搬官方的无限等待；主代理继续负责状态、时序与实板排查。
5. 抓包对应 Keil 示例，不能据此断言当前 SDCC 固件在同样环境下应有完全相同的停止行为。
6. 延续用户已纠正的事实：没有确认此前 _flash 能恢复正常运行。本报告不使用该前提。还原设置对比中官方保持 FF/AF，仅将 77 改为 F7；FD/BE 是 CLion 的改动，不能写成两边都修改。
