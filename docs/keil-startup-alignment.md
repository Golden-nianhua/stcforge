# USB-ICE 启动流程与 Keil 对齐

2026-11-15，生产入口 `stcforge gdbserver --usb` 改用 `IceSession.initialize_debug()`，不再执行原来的 `version → halt → 超时后读取状态`。

## 现行顺序

1. 查询版本，要求为已核对的 V4.0。
2. 发送抓包中的特殊入口请求 `FF5A08020000FF0000009E`，校验全零内容的事件确认。
3. 从确认收到后等待 2 秒。
4. 查询完整 46 字节 CPU 状态，确认 PC=FF0000。
5. 启动 GDB 服务，等待客户端。此阶段不发送 halt 或 run。

这建立从入口开始的新调试会话，具有改变执行位置的副作用，不是无侵入地接回原来的暂停位置。通用 `set_pc` 仍不开放。任一阶段失败就终止，不用后备暂停掩盖启动失败。

对应原始 `keil sma.pcapng` 的 1733/1735、1737/1739、1741/1743 帧；原始 SDCC 抓包中多出的 237 暂停请求已从生产启动路径去除。

## 本轮实板结果

日志：`.cache/ice-keil-flow-production-20261115.jsonl`。测试使用生产 `IceSession.initialize_debug()` 和 `IceTarget`，通过 hidapi 访问当前板卡，没有重新下载固件或写断点。测试前独立只读核对简单 SDCC 固件的 1,914 个有效字节全部一致，见 `.cache/ice-keil-flow-image-20261115.jsonl`。

| 日志时间 | 行为 | 结果 |
|---|---|---|
| 0.016..0.019 s | 查询版本 | V4.0 |
| 0.019..0.045 s | 特殊入口请求 | 收到确认 |
| 2.045..2.048 s | 等待 2 秒后读取 CPU 状态 | PC=FF0000，完整初始状态与 Keil 一致 |
| 2.050..2.053 s | 继续运行 | 收到确认 |
| 3.055 s | 请求暂停 | 1000 ms 内无回复 |
| 4.063 s | 后备状态查询 | 同样超时 |

启动报文顺序和两秒等待已对齐，实板入口初始化通过；全速运行后恢复暂停仍未通过，不能把本改动宣称为调试失联已修复。旧诊断工具 `--official-start` 保留先读取 PC 的保护逻辑，它不是本次生产顺序验收所用入口。

实测运行失败后尝试通过真实 CLI 启动服务，设备打开返回 open failed，服务未监听，真实 GDB 因而无法连接；不能将这次尝试记为实板 GDB 联调通过。

## 回归结果

Windows uv 环境下完整 136 项测试通过，无跳过；启用了本机 SDCC 和真实 MCS-251 GDB 的离线联调。新增测试固定真实启动报文、ACK 后等待、快照校验和 CLI 不补发暂停，并覆盖失败清理。离线测试通过不替代上述实板运行结果。
